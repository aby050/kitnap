# Contributing to Kitnap

Thanks for helping make Kitnap better. This guide explains how to propose changes so they can be reviewed and merged quickly.

## Before you start

- **Read [`notes/DECISIONS.md`](notes/DECISIONS.md).** It records choices that were made on purpose and the
  alternatives that were rejected. If your idea reverses one, open an issue first and explain what changed.
- **Open an issue for anything larger than a bug fix** so the approach can be agreed before you write code.
- By contributing you agree that your contribution is licensed under the project's
  [license](LICENSE) and that the maintainer may also use it in the published app.

## Principles

- **Honest by default.** No fake numbers, invented reviews or dark patterns. Every control must do what it says.
- **Escape hatches stay free.** Emergency calls and other break-glass paths must always work, on every blocking screen.
- **Loosening is slower than tightening.** Changes that weaken a user's own rules should keep their delays and guardian checks.
- **Local-first.** Don't add a backend, analytics SDK or new network call without discussing it first.

## Development setup

See [Getting started](README.md#getting-started) in the README. In short:

```bash
npm install
npm run android   # or: npm run ios
```

Native code lives in `modules/`, `targets/` and `plugins/`. `android/` and `ios/` are generated by
`expo prebuild` and are not committed — make native changes through a config plugin or a local module.

## Making a change

1. Fork the repo and create a branch from `master`: `fix/…`, `feat/…` or `docs/…`.
2. Keep each pull request to one concern.
3. Run `npx tsc --noEmit` — it must pass with zero errors.
4. Test on a real device for anything touching blocking, schedules, permissions or purchases,
   and say which platform and OS version you used.
5. Include screenshots or a short screen recording for UI changes.

## Code style

- TypeScript in strict mode; avoid `any`.
- Function components and hooks. Keep screens in `src/main` or `src/onboarding`, logic in `src/data`.
- Use the design tokens in `src/design/tokens.ts` rather than hard-coded colours and sizes.
- Comments explain *why*, especially around platform quirks.

## Commit messages

Use the imperative mood and describe the effect: `Fix shield re-firing after a bailout`, not `fixed bug`.
